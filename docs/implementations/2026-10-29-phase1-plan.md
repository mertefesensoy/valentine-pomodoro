## 1. Problem / Motivation

v1.4 is the first release existing iOS users see from the rehaul. One release now carries all of these:

- the SDK 54 → 58 jump (already done in Phase 0)
- a full visual redesign
- a navigation rewrite (Expo Router)
- a storage migration (AsyncStorage → MMKV) that holds every user's stats and notes, Bengisu's included
- the re-render refactor that replaces the chain the timer text depends on (plan §4.5, finding F1)

Each of these has a failure mode that tests on this machine can't fully see: a frozen timer, lost data, a release-only crash. Because you chose one release over two, this plan **orders the work so that each risky change lands behind a gate** that already exists and has been seen to fail. The two gates the rest of the plan hangs on are:

- **`timerTextTicks`**, the guard that the timer text still changes every second
- **the Reassure render-count baseline**: 14 renders today for a settings-only component during 10 s of a running session

## 4. Mathematical / Statistical Details

### 4.1 Contrast check (C1)

For a colour with 8-bit sRGB channels $R_8, G_8, B_8$, each channel is normalised and linearised:

$$c = \frac{C_8}{255}, \qquad c_{\text{lin}} = \begin{cases} \dfrac{c}{12.92} & c \le 0.04045 \\[4pt] \left(\dfrac{c + 0.055}{1.055}\right)^{2.4} & c > 0.04045 \end{cases}$$

The relative luminance is $L = 0.2126\,R_{\text{lin}} + 0.7152\,G_{\text{lin}} + 0.0722\,B_{\text{lin}}$.

For two colours with $L_1 \ge L_2$, the contrast ratio is

$$\text{CR} = \frac{L_1 + 0.05}{L_2 + 0.05} \in [1, 21].$$

The script checks every text/background pair the token file declares:

- **CR ≥ 4.5** for body text
- **CR ≥ 3** for large text (≥ 18 pt regular or ≥ 14 pt bold) and for icons and other non-text UI

It fails CI on any miss and prints the pair and its ratio. Semi-transparent colours are composited over their background before the check, using $c = \alpha c_{fg} + (1 - \alpha) c_{bg}$ per channel in sRGB space, the same model the platforms use to draw them.

### 4.2 When the clock store emits (B4)

Let $E$ be the session's `endAt` and $r(t) = E - t$ the remaining milliseconds. The display today is $\lfloor r / 1000 \rfloor$ seconds (`formatTime`), and B4 keeps that convention.

Today a free-running `setInterval(1000)` re-renders on a fixed phase unrelated to $E$, so the shown second can lag the true one by up to 999 ms.

The clock store instead schedules its next emission for the instant the shown value changes:

$$d = \big(r \bmod 1000\big) + \varepsilon, \quad \text{with } d = 1000 + \varepsilon \text{ when } r \bmod 1000 = 0,$$

where $\varepsilon \approx 4$ ms absorbs timer jitter. On every emission it recomputes $r$ from `Date.now()`, so errors never accumulate. The worst-case display lag becomes $\varepsilon$ plus the timer's latency, instead of up to 1 s.

Properties the tests pin:

- exactly one emission per displayed second
- none while paused
- completion fires once, when $r \le 0$

### 4.3 Render-count target (B4, Reassure)

The baseline scenario for the settings-only component has 14 renders, measured. The breakdown is **confirmed by an instrumented run (A2, 2026-10-29)**: mount and hydrate (2), start (1), 10 one-second ticks (10), stop (1).

Mount and hydrate both happen inside RNTL's `render()`. Under Jest all six store loads batch into one commit, so on a phone, where the loads resolve separately, hydrate may take more than one commit.

After B4 that component does not depend on the clock, so the target is **≤ 2** (mount and hydrate; possibly 1, since MMKV hydrates synchronously).

The `<TimerText>` leaf is expected to render $1 + n$ times: once at mount, plus once for each of the $n$ times its displayed value changes. (Corrected in A2: an earlier version counted only the seconds that pass.) The scenario's stand-in leaf shows `00:00` while idle, so its value changes 12 times:

- at start, to `25:00`
- at each of the 10 ticks
- at stop, back to `00:00`

That makes **13** the B4 floor for the leaf, against 14 today; only the hydrate commit goes. The real `<TimerText>` may be one lower, if its idle text is the configured duration. The Timer screen contains the leaf, so it keeps committing every second; its rule is "doesn't go up".

Reassure counts are deterministic under fake timers. Its timing figures are means over the runs and are treated as advisory, as in CI today.

### 4.4 Sound export headroom (D4)

A level $L$ in dBFS corresponds to a linear amplitude factor $g = 10^{L/20}$, so −1 dBFS is $g \approx 0.891$ of full scale.

Lossy AAC encoding reconstructs the waveform from frequency-domain coefficients. The decoded signal can peak *between* the original samples, and above the PCM peak: "inter-sample peaks", typically a few tenths of a dB on bright, transient sounds like chimes.

A file normalized to −0.1 dBFS (SoundCraft's `--normalize`) can therefore clip after decoding. So each sound is bounced, then scaled to a −1 dBFS sample peak before encoding, leaving about 1 dB of room for those overshoots.

The check: decode the shipped `.m4a` with ffmpeg and confirm its peak stays below 0 dBFS (`ffmpeg -i x.m4a -af volumedetect -f null -`, reading `max_volume`).

## 5. Design Decisions and findings

**Finding 1 — lazy loading does not shrink the native bundle.** On iOS and Android, Hermes ships **one** precompiled bytecode bundle. `React.lazy` and inline requires defer when a module is *evaluated*, which helps cold-start time, but the module is still in the bytecode. So B1 improves TTI but **cannot recover the +19 % bytecode** recorded in the SDK 58 upgrade. Neither can it meet plan §6.2's "≥ 25 % smaller startup bundle" by itself; that wording assumed chunking, which only exists on the web.

**Decided (your call, 2026-10-29): task B1b.** `airports.json` (648 KB of JSON) moves out of the module graph into a bundled asset, read and parsed only when Fly opens. That removes it from the bytecode while keeping the real map unchanged until Phase 4b replaces the dataset. It is about a day of work. The bundle budget is then re-baselined against the measured result.

| Decision | Alternatives considered | Why this one |
|----------|------------------------|--------------|
| Gates first (A0–A3), then architecture, then visuals | Visual redesign first, so users see progress | With one release, the risky changes must sit on tests that already exist and have been seen to fail. The visuals depend on stores and routes, not the other way round. |
| Guards render the **real** screens (A1) | Keep the probe-only test | Plan §4.5 asks for both screens. A probe can pass while the screen's own subscription is wrong. |
| Migrator writes its flag **last**; AsyncStorage kept for one release | Delete AsyncStorage after copying; a flag first | A crash before the flag just re-runs an identical copy. Keeping the source makes a rollback build possible. |
| Persist the v1.3.1 default notes for existing installs | Change the defaults for everyone | An existing user who never edited notes has no `love_notes` key, so changing the defaults would silently replace Bengisu's notes. This honours "her install keeps its notes". |
| Keep the `⌊r/1000⌋` display convention | Switch to a ceiling countdown (shows 25:00 for the first second, 00:01 for the last) | No behaviour change hidden inside a refactor. Easy to switch later as its own decision. |
| Stage C alongside Stage B | Strictly sequential | Art and tokens touch no app code paths until D1. |
| Reserve the partner slot in Classic now (C4) | Lay out for solo, re-layout in Phase 3 | `DESIGN.md`: both partners always visible. Reserving the slot avoids redesigning Classic twice. |
| AdMob stays on 16, test ids stay on Android | Fix ads now | The plan puts the AdMob 17 rewrite, real ids and consent in Phase 5. v1.4 changes only where the ad sits, not its policy. |
