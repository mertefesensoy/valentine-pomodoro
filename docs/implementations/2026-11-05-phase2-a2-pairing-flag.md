## 1. Problem / Motivation

Phase 2 has no integration branch. Every task merges into `master` on its own, and `master` must stay releasable all the way through ([BRANCHING.md](../process/BRANCHING.md)). So the pairing screens need one switch that hides them until Stage F, and every later task needs that switch to exist first.

The owner's account decisions also change what ADR-0021 records. It still describes anonymous sign-in for solo use, a linked Apple, Google or email account for pairing, and (through the rehaul plan) links on a domain. A later reader of those ADRs would build the wrong thing, so the change gets its own decision record.

Requirements: [FR-ACC-001](../srs/SRS.md#fr-acc-001), [FR-ACC-002](../srs/SRS.md#fr-acc-002), [FR-PAR-001](../srs/SRS.md#fr-par-001).

## 3. Implementation Approach

**`PAIRING_ENABLED`** is an exported constant typed `boolean`, not the literal `false`.

- **Contract:** no inputs, no side effects. It is read at module load and never changes during a process.
- **Why the wider type:** with the literal type, TypeScript treats `if (PAIRING_ENABLED)` as always false and reports the branch as unreachable, and the screens behind it would stop being type-checked in the way the rest of the code is.
- **Nothing reads it yet.** D1 adds the first reader, the pairing entry point. A solo user sees no change on `master` until Stage F.

**The flag doesn't shrink the bundle.** Code behind it still ships in the one Hermes bytecode file, so size is A1's question, not this flag's. It controls what a person can reach, and nothing else.

**The test** asserts the value directly. It exists so that a stray flip fails CI, and so that Stage F's flip (task F1) has to touch the test and say why.

## 5. Design Decisions

| Decision | Alternatives considered | Why this one |
|----------|------------------------|--------------|
| A constant in `features.ts` | A remote flag; an environment variable per EAS profile | `features.ts` is already the app's one point for feature gates. A remote flag needs a server call, and a solo user must never make one. A per-profile variable would let TestFlight differ from the App Store build, which is the build the owner checks |
| One flag for everything in pairing | One flag per screen | The plan names one switch. Stage F turns the whole feature on at once, so finer switches would only add states nobody tests |
| A new ADR, with notes on ADR-0021 and ADR-0029 | Rewriting those ADRs in place | ADRs record what was decided when. ADR-0021's own decision (Supabase) still stands, and only its auth paragraph is replaced |
