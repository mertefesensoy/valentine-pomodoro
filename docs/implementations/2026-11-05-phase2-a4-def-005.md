## 1. Problem / Motivation

When a session starts or resumes, the app schedules one local notification for its end, and keeps the notification's id on the session's slot so that pause, skip, reset or a mode switch can cancel it ([FR-NTF-001](../srs/SRS.md#fr-ntf-001)). Starting a session mustn't wait on the system indefinitely (the first call can show the permission prompt), so the call is raced against a 1 s timeout.

**The defect (DEF-005):** the timeout wins the race, the slot records `null`, and the real scheduling carries on underneath. Its id is thrown away when it arrives, so nothing can cancel that notification, and a paused or skipped session may still alert.

The SRS row cites `useTimer.ts`, but the same race is in four places: `useTimer.ts`'s start and resume, and `FlyModeScreen.tsx`'s start and resume. All four are fixed, so Fly doesn't keep a copy of the bug.

## 3. Implementation Approach

The screens keep the timeout, because starting a session still mustn't hang. What changes is what happens to the id afterwards.

**`scheduleSlotEnd(kind, endAtMs, title, body): Promise<string | null>`,** for a session about to start.

- **Returns** the id if it arrives within 1 s, or `null` at 1 s if it hasn't. It rejects only if scheduling fails within the 1 s, which callers already catch.
- **Side effect:** an id that arrives after the deadline is kept on the slot, or cancelled (the rule below). A failure after the deadline is logged, never thrown, since nobody is waiting for it.

**`rescheduleSlotEnd(kind, endAtMs, title, body): Promise<void>`,** for a session that has just resumed, so its slot already exists.

- The same deadline. An id is put through the same rule whether it arrives in time or late, because the person can pause again within that 1 s, and storing it blindly would leave a paused session with a live alert.

**The rule for an id that comes back (`keepOrCancel`).** It is kept only when both hold, and otherwise cancelled:

1. **The slot of that kind is running.** A pause, skip, reset or switch has left it stopped, paused or gone, so an alert for it must not fire.
2. **This is the newest schedule call for that kind.** Pause and resume again, and the first call's id is out of date: the slot is running, but that notification carries the old end time, so it would fire early. A counter per kind, kept beside the hook, tells them apart. Nothing needs to bump it on a pause, since condition 1 covers that.

**What's left alone.** Scheduling only, as the plan says. The session store's `start`, `pause`, `resume`, `stop`, `switchTo` and its completion engine don't change; the hook reads the clock and calls the existing `setSlotExtras`, as `useTimer` already does. The clock store and the v1.3.1 migration aren't touched.

## 5. Design Decisions

| Decision | Alternatives considered | Why this one |
|----------|------------------------|--------------|
| Keep the 1 s deadline and deal with the late id | Remove the race and await the id; lengthen the timeout | Awaiting would hold the start of a session behind the permission prompt. A longer timeout only moves the bug |
| Cancel a late id whose slot has moved on | Store it anyway, and let the next action cancel it | A slot that's paused has no next action until the person returns, and the alert would fire first |
| A counter for "newest call" | Compare the notification's end time with the slot's | The slot's end time moves with `extend` and pause, so a comparison would need a tolerance. A counter has no such edge |
| One helper in `useNotifications.ts`, for all four places | Fix `useTimer` only, as the SRS row cited | Fly had the same bug. Two copies of a race is how the second one stays broken |
| A test through the real session store with fake timers | A mocked store | The rule reads the store's state, and a mock would pass whatever the rule read |
