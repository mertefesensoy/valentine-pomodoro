## 1. Problem / Motivation

This repo is public and the publishable key ships in the app, so anyone can call the database directly with their own account. The only thing keeping strangers out is what the database itself allows, and a policy that's wrong fails silently. So the rules are written once, and tested as the people they protect, in CI, where a failing policy blocks the merge.

## 3. Implementation Approach

**Reads go through policies, and writes go through functions.** `authenticated` gets `SELECT` on five tables and no `INSERT`, `UPDATE` or `DELETE` anywhere, so a day can only change through `report_day`'s `max` (plan §4), and a note only through `send_note`'s limits. `invites` has no grant and no policy: it's reached only through functions. `anon` gets nothing.

| Table | Who can read a row |
|---|---|
| `profiles` | Yourself and your partner, and only `id`, `display_name`, `tz`, `locale` and `created_at`, granted by column |
| `couples`, `couple_members` | The couple's members |
| `daily_stats` | Yourself and your partner, for `owner_kind = 'user'` |
| `love_notes` | Its author and its recipient |
| `invites` | Nobody, directly |

**Function contracts:**

- `is_couple_member(target_couple uuid) returns boolean`: whether the signed-in person belongs to that couple. `stable security definer`, with an empty `search_path`. It must be definer: a policy on `couple_members` calls it, and it reads `couple_members`, which would recurse otherwise.
- `is_partner_of(other_user uuid) returns boolean`: whether that person is the signed-in person's partner, and never themselves. The same properties.

**`auth.uid()` is wrapped as `(select auth.uid())`,** so Postgres evaluates it once per query rather than once per row (rehaul §4.3, Supabase's guidance).

**The tests** set the role and the JWT claims as PostgREST does (`set local role authenticated`, `set local request.jwt.claims`), which is what `auth.uid()` reads. They assert the privileges themselves as well as the policies' results, since RLS with no grant and a grant with no RLS would each pass half of the checks.

## 5. Design Decisions

| Decision | Alternatives considered | Why this one |
|----------|------------------------|--------------|
| No write policies at all | `INSERT` and `UPDATE` policies for a person's own rows | A direct `UPDATE` could lower a day and defeat `report_day`'s `max`, and skip a note's limits. Functions are the one write path |
| `SELECT` on `profiles` by column | A separate table for the limit's state | Keeps the plan's six tables, and the test pins that nobody can read those columns |
| Grant reads at all, when the app only calls functions | No table grants | The plan's rules are about reads, Phase 3's Realtime needs them, and RLS is what's actually tested |
| Test privileges and results both | Results only | Each alone can pass for the wrong reason |
