## 1. Problem / Motivation

A paired person's screens read one thing: `home_snapshot`. It has to show the last known values immediately, including offline, and refresh quietly. A solo person must not pay for any of it. This task also holds the test that proves that, over a real launch of the Timer.

Requirements: [FR-PAR-003](../srs/SRS.md#fr-par-003), [FR-ACC-001](../srs/SRS.md#fr-acc-001), [NFR-PERF-003](../srs/SRS.md#nfr-perf-003).

## 3. Implementation Approach

**The gate.** `schedulePairedRuntime()` lives in a module with no SDK imports. Only when `PAIRING_ENABLED` is on and `hasAccount()` is true does it ask `runAfterInteractive` to `import()` the runtime. So a solo launch evaluates nothing here beyond one read of a flag, and Query, the client and the Keychain stay unloaded. An imported module is still in the one bytecode bundle, as the plan's Finding 1 says, but it's never evaluated.

**`useHome()`** calls `useQuery` with this file's own `QueryClient`, passed as its second argument, so no provider has to sit above the tabs, and the solo tree stays exactly as it is. Only the paired components, loaded with `React.lazy` in D1 and D2, import it.

**The options:**

- `staleTime` is 30 seconds, so a tab switch doesn't refetch.
- `gcTime` is `Infinity`, not the 30 days that `maxAge` uses. A timer that long overflows `setTimeout`'s 32 bits and fires at once, which dropped the query before the persister could save it. The persistence test caught this.
- `networkMode: 'offlineFirst'`, so the query runs and fails normally when offline, and cached data stays on screen.
- `retry` is one try, and none for `SessionEnded`, since retrying can't help.
- `refetchOnWindowFocus` is off, because React Native has no window focus. `runtime.ts` refreshes on `AppState` instead.

**The persisted cache** uses `persistQueryClient` with the sync persister over `appStorage`, under one key, `home_cache_v1`. That's what shows last known values on a cold start with no network, and how an undelivered note still shows offline (plan D3). `clearHome()` removes it at unpairing and deletion.

**`startPairedRuntime()`** starts once per launch. It refreshes after the first frame, and each time `AppState` becomes `active`. It holds no connection, so nothing stays open while a person focuses (plan §5).

**`invalidateQueries` is the only refresh.** Nothing polls in the background, apart from the pairing sheet's 10-second check while it's open, which D1 adds.

## 5. Design Decisions

| Decision | Alternatives considered | Why this one |
|----------|------------------------|--------------|
| No `QueryClientProvider` | One around the tabs | A provider at the root would load Query for everyone, which is what this exists to avoid |
| Pinned exact, at 5.104.5 | The latest, 5.106.1, published today | The project's rule is a release at least two weeks old. Those three packages move together |
| `home_cache_v1` in plain MMKV | The Keychain | It holds a partner's name and day, not a credential, and the Keychain's size limit would get in the way. It's removed at unpairing and deletion |
| A solo-launch test over the real Timer | A test of the gate alone | A static import added anywhere later would pass a gate-only test and still load everything |
