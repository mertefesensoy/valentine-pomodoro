## 1. Problem / Motivation

The app has no backend. Everything that makes it a couples product, from 1.6.0's shared room onward, needs accounts, a pairing between two people, and a database whose rules keep strangers out. Phase 2 builds that foundation.

Built exactly as the rehaul plan wrote it, 1.5.0 would ask people to sign in and pair, and then nothing would happen until 1.6.0. So the owner added one small visible payoff: you can see your partner's day. It also proves the whole stack with real data (sign-in, row-level security, a server write, a server read), without touching the session engine.

Two constraints shape the plan:

- **Solo users must lose nothing.** FR-ACC-001 says the timer, stats and notes work fully without an account. For them 1.5.0 adds no network call, no account and no change to what the app collects, beyond crash reports (§3 E1).
- **The app can't simply grow.** NFR-PERF-002's ceiling is the bytecode 1.4.0 shipped, 4,292,868 B, and 1.4.1 measures 4,292,796 B. Hermes ships one bytecode bundle, so a lazy import doesn't shrink it (Phase 1 plan, Finding 1). This phase adds three or four SDKs, so the ceiling is met head-on in Stage A, before any of them is merged.

**Not in 1.5.0:** invite links and the domain, Google and email sign-in, anonymous accounts, partner notes, presence, cheers, Realtime, server pushes, the shared room (all Phase 3); Plus and RevenueCat (Phase 5); Android.

## 4. Mathematical / Statistical Details

**How hard a code is to guess.** The alphabet is A–Z and 2–9 without the look-alikes I, L, O (0 and 1 are already out): 31 symbols, so there are 31⁶ = 887,503,681 codes. If N codes are live, and someone makes k guesses, the chance that at least one hits is about kN / 31⁶ while that's small. With 1,000 live codes, and `redeem_invite` limited to 5 failed tries an hour per account, one account makes at most 120 guesses in a day: 120 × 1,000 / 887,503,681 ≈ 0.00014, or about 1 in 7,400. So the limit and the expiry matter more than the code's length. As a further guard, the person redeeming sees whose code it is before confirming, and either partner can unpair.

**Why a replayed report can't inflate a day.** `report_day(day_key, focus_ms, sessions, goal_hit)` is idempotent and order-independent, because the server keeps the largest value it has seen for that day: `focus_ms' = max(focus_ms, reported)`, and the same for `sessions`. `goal_hit` is a logical OR. Local totals for a day only grow, so a late or repeated report can't lower or double anything. Reinstalling, which starts the phone's count from nothing, can't erase the server's day either.

**Whose "today".** A day's key is the reporter's local date, as the app already keeps it. `home_snapshot` finds the partner's today from `profiles.tz`, so a couple in two time zones each see the other's own day. If a partner has no row for that date, the card says nothing yet today, rather than showing yesterday's.

**The size budget.** For each SDK, cost = bytecode with it − bytecode without it. The ceiling for 1.5.0 is the owner's call after A1, at 4,292,868 B + the kept costs − any trim.

## 5. Design Decisions

| Decision | Alternatives considered | Why this one |
|----------|------------------------|--------------|
| An account only at pairing | Anonymous sign-in at first launch (rehaul §4.1) | **The owner's choice.** Anonymous accounts would mean a server row for every install, with no automatic cleanup. Supabase strongly recommends a CAPTCHA with them, and Apple's deletion rule also covers guest accounts. Solo use needs none of it |
| Sign in with Apple only | Add an email link or Google | **The owner's choice.** A native-only setup needs no secret rotation (Supabase's Apple guide). Email links need a paid sending service, since Supabase's built-in one is limited to 2 emails an hour and team addresses. The app stays within Guideline 4.8 because no other third-party login exists |
| Codes only | Links on a new domain; links on `vercel.app` | **The owner's choice.** No domain or website work now. The cost is one more step for the partner, and the same code flow is the fallback once links arrive |
| Read-only partner's day from client-reported totals | Server-credited sessions, now | Server-owned sessions are Phase 3 (ADR-0022). A person can only misreport their own numbers to their own partner, so the risk is small until then. Phase 3's trigger on `session_credits` takes over the same `daily_stats` row |
| Refresh on foreground | Realtime now | Realtime arrives with Phase 3, which needs it. A day's totals don't need to be live, and this avoids a connection for paired users' whole session |
| Revoke the Apple token by asking the person to confirm with Apple at deletion, then exchanging that fresh code | Keep a refresh token on the server from first sign-in | Apple says to use its REST API to revoke tokens. This way, no long-lived Apple token sits in the database, and a destructive action gets a real confirmation. The cost is that the `.p8` key is needed even though sign-in is native-only, so it lives only in Supabase secrets. It is a review risk under Guideline 5.1.1(v), so B3 tests it end to end |
| One constant flag, many small pull requests | A long-lived `phase2` branch | BRANCHING.md now forbids the branch, and the flag keeps every merge releasable |
| pgTAP in CI only | Docker Desktop on this machine | This machine has neither Docker nor the Supabase CLI, and CI is the gate anyway. Open item 3 |

## 6. Verification

**Exit criteria for 1.5.0:**

- [ ] Two accounts on two physical iPhones pair by code, and each sees the other's day update after a focus session and a return to the foreground.
- [ ] **A solo install never contacts Supabase,** and its timer, stats and notes work offline exactly as on 1.4.
- [ ] 1.4.x's data survives the update on a real iPhone (NFR-REL-002).
- [ ] pgTAP is green in CI (NFR-SEC-001), and the N+1 review is clean.
- [ ] Unpairing and deleting an account work, the partner keeps their own history, and the Apple token is revoked.
- [ ] Export gives all of that person's data as JSON.
- [ ] Cold start against NFR-PERF-001 and bytecode against the new NFR-PERF-002 ceiling are recorded, each met or decided by the owner.
- [ ] **No `audio` in `UIBackgroundModes`** (`appConfig.test.ts`), and App Review raises nothing about accounts or deletion.

**Open items for the owner's approval.** Each is the recommendation unless changed:

1. **Don't upload stats history and notes yet.** FR-MIG-003 uploads them at first sign-in, but nothing in 1.5.0 reads them: the partner's day only needs today. The phone stays the source of truth, so waiting loses nothing, and less personal data goes to a server (NFR-PRIV-001). It moves to Phase 3, when notes are delivered and couple stats begin.
2. **Leave out the `events` analytics table for now.** No question in 1.5.0 needs it, and Sentry covers crashes. It comes back when there's something to measure.
3. **pgTAP in CI only,** with no Docker Desktop on this machine.
4. **Fix DEF-005 in this phase** (a paused or skipped session may still alert if scheduling is slow; its slot was left to the owner). It is notification scheduling, not the session engine.
5. **A code lasts 24 hours,** and creating a new one cancels the old one.
6. **Whose second iPhone** runs the two-phone check. Tell the build session when Stage F starts.
