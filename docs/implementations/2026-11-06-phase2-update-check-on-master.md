# 2026-11-06 — Phase 2: 1.4.2's update check fix comes to master

**Status:** Done, with the guards green. The fix itself is on a device already, in 1.4.2's build; with 1.5.0 it's rechecked at F2.
**Branch:** `feat/phase2-update-check-fix`, one pull request into `master`.

---

## 1. Problem / Motivation

1.4.2 was built from the `v1.4.1` tag, so that a patch didn't carry 1.5.0's unreleased work, and its fix sits on `fix/1.4.2-update-check`. It has to reach `master` before 1.5.0 ships, or 1.5.0 would bring the bug back: "Check for updates" saying you're up to date for a day after a release.

The plan was to wait for Apple's answer on 1.4.2. The owner, 2026-11-06, asked when it should come in: "Bring it in now (Recommended)", so that the first TestFlight build can be the release candidate.

## 2. What Changed

| File | Change |
|------|--------|

| `app.json`, `package.json`, `package-lock.json` | Unchanged at 1.5.0: this side of the conflict won. |
| `docs/srs/SRS.md` | NFR-PERF-002 keeps 1.5.0's ceiling, and adds 1.4.2's size to its history. |
| `docs/process/RELEASE.md` | Step 9 keeps the `-submitted` tag from `master`, and step 10 gains the branch's way to check that a version is live. |
| `docs/testing/TRACEABILITY.md` and the backlink blocks | Regenerated by `check-docs --write`. |

## 3. Implementation Approach

A merge of `origin/fix/1.4.2-update-check` at `e76d6bd`, not a cherry-pick, so that git knows the fix is here and a later merge of that branch has nothing to do. Their branch isn't pushed to, and the 1.4.2 session has been told not to open a pull request of its own.

**If Apple asks for changes to 1.4.2,** those commits have to come across as well.

| Decision | Alternatives considered | Why this one |

| A merge | A cherry-pick | Its commits keep their ids, which the CHANGELOG names |
