# 2026-11-06 — 1.4.2: the update check finds new versions when they're out

**Status:** In progress: submitted on build 62, and App Review's answer is pending
**Branch:** `fix/1.4.2-update-check`, from tag `v1.4.1` ([BRANCHING.md](../process/BRANCHING.md) rule 4)

## 1. Problem / Motivation

A phone on 1.4.0 told its owner "You have the latest version (1.4.0)" after 1.4.1 was live. The [audit](2026-11-06-update-check-audit.md) found why: Apple's CDN keeps each exact lookup URL for up to 24 hours, and the app has always called the same URL. The automatic check also runs only on a cold launch, so a new version can stay hidden for much longer than a day on a phone that keeps the app suspended.

The owner's decisions, 2026-11-06, in their words:

- **Where the fix goes:** "A 1.4.2 patch first".
- **Whether to check on returning to the app:** "Yes, every 6 hours at most (Recommended)".
- **Whether a prompt may appear during a running timer:** "No, wait until it's idle (Recommended)".

`master` already holds 1.5.0's work, including Supabase and new native modules, so 1.4.2 branches from the release tag and goes forward to `master` in its own pull request ("How it ships" in §3 has when).

**What this patch can and can't do:** the fix helps from the release *after* 1.4.2. Phones on 1.4.1 or older still run today's check, so they can take up to 24 hours to see 1.4.2 itself. And App Review takes one version at a time, so 1.5.0 can't be submitted while 1.4.2 is in review.

## 3. Implementation Approach

**A. The URL.** `iosLookupUrl(now, force)` is pure and returns the lookup URL with `&cb=<value>`:

- **Automatic check:** the value is the current hour, `floor(now / 1 h)`, so everyone shares one cached copy each hour and the answer is at most an hour old.
- **The button:** the value is `now` in milliseconds, so a press always reaches past both caches.

This covers Apple's CDN and the phone's URL cache together, because both key on the exact URL.

**B. The re-check.** After the launch check has started, an `AppState` listener checks again on `active`, if the last answer is at least 6 hours old or the last check failed. The listener only starts once the launch check has, so a launch's own `active` event can't run ahead of the first frame (Phase 1 B7). Someone who tapped "Not now" can be asked again after 6 hours.

**C. No prompt on a running timer.** An automatic check that finds a newer version while a focus, a break or a Fly session is running shows nothing and doesn't count as an answer, so the next return to the app asks again.

- **It covers the launch check too.** Someone who opens the app and starts the timer before the answer arrives isn't interrupted, which the old launch check could do.
- **The button always answers,** because someone asked.
- **If the session ends with the app still open,** the prompt waits for the next return or launch. It doesn't appear on top of the session's end, with its love note and possible ad.
- **The timer's state is only read,** through `useSessionStore.getState()`.

**D. The state.** `lastCheckAt` replaces `sessionChecked`. The audit asked for it to be set only after a successful answer, so that a failed check retries. It's set when a check starts and cleared if there's no answer, which gives the same retry and also lets the two mounts (the root and Settings) share one check when both ask at once. A forced check ignores it and also sets it.

**Unchanged:** the launch check still waits for the first frame; the comparison, the alerts and their text; `update.json`; Android's fetch; the session engine, the clock store and the v1.3.1 migration. No new strings, so no Turkish copy to review.

## 4. Mathematical / Statistical Details

A release at time `T_r` is visible to an automatic check at time `t` once `t` falls in a later hour bucket than the one holding a pre-release copy: `floor(t / 1 h) > floor(T_r / 1 h)`. So the lag is under 1 hour, against up to 24 hours before ([audit §4.1](2026-11-06-update-check-audit.md)). A button press has no lag from these caches. The first automatic check in a bucket may also be up to 6 hours later on a phone that stays open, because of the re-check's limit.

## 5. Design Decisions

| Decision | Alternatives considered | Why this one |
|----------|------------------------|--------------|
| Ship as 1.4.2 from `v1.4.1` | Inside 1.5.0; from `master` | **The owner's choice.** `master` holds 1.5.0's unreleased code, which a patch mustn't carry |
| Hourly value for automatic checks | A new value on every launch | Keeps the CDN useful, which Apple asks for, at a cost of at most an hour |
| Re-check at most every 6 hours | Every return | Too many requests and prompts. iOS can keep an app suspended for days, so launch-only isn't enough |
| No automatic prompt during a running session, launch check included | Prompt anyway; guard only the new re-check | **The owner's choice,** "wait until it's idle". Guarding the prompt itself, not just the start of the check, also covers a timer started while the answer is on its way |
| The prompt waits for the next return or launch once idle | Watch the store and prompt when the session ends | That moment already has the love note and possibly an ad. Watching the store would also tie this hook to the session's lifecycle |
| Set `lastCheckAt` at the start and clear it on failure | A separate in-flight flag and a time set on success | One variable gives both behaviours |
| No "Open App Store" button on "You're up to date" | Add one | It needs new Turkish copy, and a fresh answer removes most of the reason |
