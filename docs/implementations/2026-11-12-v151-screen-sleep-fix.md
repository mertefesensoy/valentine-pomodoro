## 1. Problem / Motivation

The owner and their girlfriend found that the phone locks itself during a session, in the Ring, the facing pages and Fly. [The audit](2026-11-12-screen-sleep-audit.md) found the cause: nothing in the app has ever kept the screen on, so iOS's Auto-Lock (30 s to 5 min with no touch, 30 s in Low Power Mode) locks the phone a few minutes into any session. Development builds hide it, because Expo's dev wrapper keeps the screen awake for as long as the app is open.

A lock doesn't break the session itself: the time is `endAt − now`, the end notification still rings, and the credit lands on return. But the person loses what they're watching and hearing. The ring and the pages go dark, Fly's hum stops (the app has no background audio mode, by DEF-009), and the finish sound and love note wait until unlock.

**The owner's decision, 2026-11-12:** build the fix with the audit's recommended answers ([audit §8.1](2026-11-12-screen-sleep-audit.md#81-the-owners-decisions)):

| # | Question | Answer |
|---|----------|--------|
| Q1 | Breaks too, or focus only? | **Breaks too:** the whole running session. |
| Q2 | While paused? | **No:** a paused session lets the screen lock. |
| Q3 | On the other tabs? | **Yes:** app-wide while a session runs. |
| Q4 | A Settings switch? | **Not in 1.5.1.** |

The owner also asked how the fix relates to sound. It does indirectly. Keeping the screen on keeps the app in the foreground, so the hum, the finish sound and the love note carry on as they do when the phone is held. The fix adds no background permission: a lock with the side button still stops the hum, as before. Keeping the hum through a manual lock would need the `audio` background mode, which this project rules out (DEF-009).

## 3. Implementation Approach

### 3.1 The rule

The screen is held while the **active slot runs and its end is still ahead**. That covers a focus, a break and a flight alike (Q1). Pausing releases it (Q2). The rule doesn't look at the tab shown (Q3).

### 3.2 The contracts

**`isSessionRunning(clock, now): boolean`** (`useKeepScreenAwake.ts:27-32`). A pure function.
- **Inputs:** the session clock and a time in ms.
- **Output:** `true` when `clock.activeKind` names a slot with `isRunning === true` and `endAt > now`.
- **Side effects:** none.
- **What it excludes:** a running slot that isn't the active one, and an ended slot still waiting for its completion handler (DEF-004).

**`useKeepScreenAwake(active: boolean): void`** (`useKeepScreenAwake.ts:59-81`).
- **Inputs:** `active`, StoreGate's `ready`, so it does nothing before the stores have hydrated.
- **Side effects:** while `active`, it evaluates the rule on mount and on every session store change.
  - When the rule turns true, it queues `activateKeepAwakeAsync(KEEP_AWAKE_TAG)`.
  - When the rule turns false, it queues `deactivateKeepAwake(KEEP_AWAKE_TAG)`.
  - When `active` turns false, or the hook unmounts while holding, it queues the release.
- **Invariants:**
  - Mounted exactly once, by StoreGate.
  - It never calls a native function twice in a row with the same direction: a local `held` flag remembers what was last sent.
  - It renders nothing and subscribes outside React (`useSessionStore.subscribe`), so StoreGate never re-renders because of it.

**`KEEP_AWAKE_TAG = 'valentine-pomodoro-session'`.** It's never Expo's default tag. A dev build's wrapper holds the default tag, and releasing that tag would end the wrapper's hold.

### 3.3 The native call queue

`enqueue(call)` chains every native call onto one promise, so calls run in the order they were made, each after the previous one has settled. It drops rejections.
- **On iOS and Android,** the module would keep that order anyway.
- **On the web,** activating waits for the browser's wake lock. A release sent before the lock arrived would find nothing to release, and the screen would stay on.
- **Why drop rejections:** a browser with no wake-lock API rejects both calls, and the only cost is a screen that may lock. The next call still runs.

### 3.4 What each session action does

| Action (`sessionStore.ts`) | Clock after it | The screen |
|----------------------------|----------------|------------|
| `start` (focus, break or flight) | active slot running, end ahead | held |
| `pause` | active slot paused | released |
| `resume` | running again | held |
| `stop` (Skip, Reset) | active slot cleared | released |
| completion (`fireCompletion`) | slot cleared | released |
| `switchTo(other kind)` | the old slot paused; the new kind active | held only if the new kind's slot runs |
| `extend` | still running, later end | held (no native call) |
| `setSlotExtras` | unchanged running state | no native call |
| the app goes to the background and returns | unchanged | expo-keep-awake drops the flag in the background and restores it on return (`KeepAwakeModule.swift:37,43`) |

## 4. Mathematical / Statistical Details

Let the clock at time $t$ have an active kind $k_t$ (or none), and let $s = \text{slot}_{k_t}$. The hold is

$$H(t) = \text{ready} \;\wedge\; k_t \neq \varnothing \;\wedge\; s.\text{isRunning} \;\wedge\; s.\text{endAt} > t$$

$H$ is evaluated at mount and at each store change $t_1, t_2, \dots$. A native call is sent only when $H(t_i) \neq H(t_{i-1})$. So the number of native calls in a session is twice its number of running stretches. For example, a focus paused once and resumed is held, released, held and released: 4 calls.

**Between store changes $H$ isn't re-evaluated.** The only time-driven change is $s.\text{endAt} \le t$. At that point the clock engine completes the session if a handler of its kind is registered. Completion clears the slot, which is a store change, so the release follows within the engine's latency ($\varepsilon = 4$ ms plus the timer's).

**If no handler is registered when the end passes** (DEF-004's waiting case), the slot stays and no store change happens, so the screen stays held until the next change. In the app, that is when the handler registers and completes the session. It's a short window: you start a session from a screen whose handler is already mounted. On a cold start, $H$ is evaluated with the current time, so an ended slot is never held (tested).

## 5. Design Decisions

| Decision | Alternatives considered | Why this one |
|----------|------------------------|--------------|
| `expo-keep-awake` pinned at **58.0.3** (`~58.0.3`, the lockfile holding 58.0.3) | 58.0.4, which `npx expo install` chose | 58.0.4 was published on 2026-11-11, the day before, and changes how the module builds on iOS (a checked-in `Package.swift` for SwiftPM). 1.5.0's binary already links 58.0.3, which works in every dev build. A patch should change one thing. |
| Subscribe to the store outside React | `useSessionStore(selector)` in StoreGate, then `useKeepAwake` in a conditionally rendered child | No re-render of the gate, which also hosts the clock engine, "subscribes to nothing that renders" (`clockStore.ts`). This also avoids touching StoreGate's synchronous-hydration invariant. |
| One hook in StoreGate | `useKeepAwake()` in Classic and in Fly | The tabs never unmount, so a screen-mounted hook would hold the screen for the app's whole life ([audit §5](2026-11-12-screen-sleep-audit.md#5-design-decisions)). |
| The end-ahead condition (`endAt > now`) | `isRunning` alone | Without it, a session that ended while the app was closed would hold the screen at launch until its handler mounts (mutation M2 in §6.1 shows the test catches this). |
| A queue for the native calls | Calling them directly | Keeps a release from overtaking a hold on the web (mutation M3). |
| Errors dropped | Logging them | The only failure is a browser without a wake lock, where nothing can be done, and a log would fire on every session. |
| No Settings switch, no background mode | A "Keep screen on" switch; `audio` in `UIBackgroundModes` | The owner's Q4; DEF-009. |
